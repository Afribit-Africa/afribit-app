# Afribit OS shell: build plan

Status: active · 2026-11-23 · supersedes the app-structure parts of `../docs/AFRIBIT_OS_EXPO_BUILD_AND_PUBLISHING_PLAN_2026-11-23.md` (its EAS/publishing sections still apply).

## 1. What we are building

Afribit OS is a **shell**. It is not a wallet. It owns boot, onboarding, the main navigation, connectivity (including the Afribit Mesh), the app registry and the rules every feature app must follow. Feature apps (Wallet, Chat, AI, Connect and later others) run inside it, but each one is **independent**:

- A crash in one feature app is contained, and the shell and the other apps keep working.
- One app's data is not readable by another. Each app gets its own storage namespace and its own keychain service.
- Apps never call each other directly. Cross-app requests go through the shell's **broker**. The broker identifies the caller itself and allows only typed, allow-listed intents.
- An app enters the registry only after it passes the **admission check** (manifest, capabilities, import boundaries). A broken or compromised app can be switched off without touching the others.

Clans is out of scope until it has been reviewed.

Revised 2026-11-24 by the owner: stable versions only, with no documented vulnerability. | SDK 56 had a documented Hermes memory regression (fixed in RN 0.86.2+). | S-07 | Brand comes from `afri/brand/tokens.json` | It overrides the PRD palette: ink, paper, gold accent, forest for positive states, Manrope type and 48 px touch targets. |
| S-08 | English and Kiswahili from day one | PRD §4.3. |
| S-09 | **Afribit identity is owned by the shell** (direction set 2026-11-24): a Nostr keypair created on the phone at onboarding, verified with a passkey (RP `afribit.africa`), quick sign-in on a new phone via passkey (PRF-wrapped identity backup; recovery words as fallback), and NIP-98 for service sign-in. Features never hold the key: they get `identity.authorize`, `vault.*` and `profile.read` capabilities. Chat inherits it with no separate sign-up. | One identity across the apps; feature isolation is preserved because keys never leave the shell. Policies are provisional and will change. |
| S-10 | **Local first: mesh traffic stays on the mesh** (owner, 2026-11-25). Chat and other mesh services work **with no internet**, only the mesh. The shell binds their traffic to the mesh Wi-Fi network (`ConnectivityManager` network binding); it never falls back to mobile data. Federation stays off. | Android routes around a Wi-Fi network with no internet by sending traffic over mobile data. That would leak mesh traffic to the carrier, tied to a nationally registered SIM. Binding has to be explicit. |
| S-11 | **Internet use is opt-in and labelled** (owner, 2026-11-25). Features that need the internet (payments, updates) use the **mesh router's uplink** by default. **Mobile data is off for Afribit by default.** A user can enable it per feature, behind a plain warning about what the carrier sees. No Google push (W-D4). | Through the mesh uplink, the ISP sees one router address shared by everyone. Over mobile data, the carrier sees the user's own SIM identity, location from towers, which servers are contacted and when. Content stays encrypted either way; metadata does not. |
| S-12 | **Money moves only through Wallet-owned confirmation** (owner, 2026-11-25). Any feature (Chat first) can *ask* to pay or request money through the broker. Only the Wallet process draws the confirmation (recipient, verification state, KES and sats, fee), then slide to confirm, then a **biometric or device-credential check that unlocks a Wallet Keystore key**. Above a user-set amount, the Wallet adds a short delay and a second confirmation. **Passkeys stay for identity** (sign-in and new-phone restore), not for approving payments. | A compromised feature can't fake or skip the confirmation. A Keystore-bound biometric proves this person on this phone, and works offline. Android passkeys normally go through Google's credential manager (conflicts with W-D4) and sync across devices, so they prove the account rather than this phone. |
| S-13 | **Onboarding offers wallet setup** (owner, 2026-11-25): one optional, skippable screen after identity, "Set up your wallet so you can pay friends in chat". It creates the wallet and asks for the backup before the first real receive. Users can set it up later from Wallet. | Makes pay-in-chat discoverable without forcing a wallet on anyone. One concern per screen (Product Flow v0.1). |
| S-14 | **Approved by the owner (2026-11-25): how the app tells our mesh from an impostor.** A network name proves nothing, since anyone can broadcast `KiberaMesh-…`. The shell shows **Verified Afribit Mesh** only when all of these hold. (1) A **signed beacon** (§4) answers a fresh nonce from the app, under a per-node key that carries a certificate from the Afribit mesh root key pinned in the release. New routers then need no app update, and the beacon carries a revocation list. (2) The beacon's `clientIp` equals the phone's own Wi-Fi address, so a relaying impostor shows up as a mismatch. (3) Mesh services (`chat.mesh.afribit.africa`, `chat-gate.mesh.afribit.africa`, the gateway) use publicly trusted certificates issued by DNS-01. They resolve to mesh addresses through mesh-local DNS, and the app pins their public keys, so an impostor that fakes DNS still can't present a valid certificate. If the name looks like ours but the checks fail, the shell shows **"This network pretends to be Afribit Mesh"**: it doesn't open the captive page, Chat stays paused, and the user sees how to report it. | Every layer an impostor can copy (name, MAC, portal page) is ignored. Every layer it can't copy (router keys, our certificates) is required. Proposal: needs owner approval. |
| S-15 | **Approved by the owner (2026-11-25): the app provisions the mesh Wi-Fi itself (phase 2).** The shell installs the mesh network through Android's `WifiNetworkSuggestion` (or Passpoint/Hotspot 2.0, which UniFi supports) as **WPA3/WPA2-Enterprise (EAP-TTLS or EAP-TLS)**, with the RADIUS server certificate pinned to the Afribit mesh CA and domain. The phone then auto-joins only access points that prove that certificate, and a fake access point can't complete the handshake. Open SSIDs with a captive portal remain for first contact and pass sales, behind S-14. | This moves impostor protection from "detect after joining" to "never join". It needs RADIUS on the mesh controller, so it's planned with the mesh owner. |
| S-16 | **Wallet ships as a companion app first (isolation I-2a, 2026-11-25).** The shell's Wallet tile opens the separately installed **Afribit Wallet** (`africa.afribit.wallet`) through `afribitwallet://`. If it is not installed, the Wallet service page offers the download. The links live only in the compiled release policy (`companion: { openUrl, installUrl }`), so a feature can't redirect them. A companion app never mounts inside the shell, even through a `/app/<id>` link. Payment requests from Chat (CR-11) will hand off over the same scheme, and the confirmation stays in the Wallet app (S-12). | Wallet 1.0.0 already works as its own app on Android and iOS. A separate app gives the strongest isolation either OS offers (its own sandbox, keystore and process, on iOS as well, where I-2 can't exist), and it needs no shared React Native runtime. Merging the Wallet into one APK (I-2) stays possible later; S-05's I-2 is deferred, not dropped. Cost: users install two apps. |
| S-17 | **One app; S-16 reversed (owner, 2026-11-26).** The Wallet, Chat and Mesh are built into the one Afribit app on Android and iPhone; nothing ships as a separate app for users to install (PRD §1.2, §6, D-005). The Wallet (pruned Blink fork: money core, accounts, auth, MFA; no map, card or learn) becomes `features/wallet` in this repo, in-process first, then its own Android process (S-05 I-2). The companion code and the separate Wallet APK are removed once the built-in Wallet works. Plan: `docs/ONE_APP_PLAN.md`. | S-16 traded the product promise for speed. Users would have to install several apps, which is exactly what Afribit exists to replace. |

## 4. Mesh onboarding contract (draft)

This reuses what the mesh repo (the public Afribit Wi-Fi repository) already does. The enrolled gateway agent sees the phone on the hotspot and calls `POST /api/mesh/gateway/context` (HMAC-signed per router enrollment). That call mints a **one-time join ticket**, valid for 120 s and bound to the phone's MAC/IP, and the captive page sends the browser to `https://wifi.afribit.africa/api/mesh/join?ticket=…&session=…`.

1. **App handoff.** The captive welcome also offers "Continue in Afribit", which opens `afribit://connect/join?ticket=…&session=…` (and a verified app link on `wifi.afribit.africa` once it is set up). The shell parses and validates the link (strict token formats, no auto-actions) and redeems the ticket with the mesh API. A successful redemption proves that an enrolled router attested this device, which gives mesh trust `attested`.
2. **Local beacon (works with the internet down).** The gateway serves a small Ed25519-signed beacon `{ v, meshId, nodeId, issuedAt, expiresAt, nonce, clientIp }` that is reachable only on mesh Wi-Fi. The app checks it against **pinned** mesh public keys shipped in the signed app, plus nonce and freshness (≤ 5 min skew). That gives `local-verified`. It is a new endpoint, to be added on the gateway.
3. A portal that is not on the pinned list is `UNTRUSTED_PORTAL`. The app never auto-submits anything to it.
4. Chat requires mesh trust `attested` or `local-verified`. Buying a pass in the app uses the existing pass/payment API (`/api/payments`, `/api/mesh/access/status`); the router whitelists those hosts before login.
5. Rank-based tunnels for trusted users off the mesh are a separate design.

## 5. Where things run

- **Source:** this git repository.
- **Install, test, build and emulator:** a dedicated Linux build host. Native Android builds use the Gradle recipe in `apps/shell`.
- **EAS:** org `afribit-africa`; the access token is never printed or committed.
- **Dependency pins:** root `overrides` hold `react-native-reanimated`, `react-native-worklets`, `expo-font` and `react-native-safe-area-context` at the versions in `expo/bundledNativeModules.json` for the current SDK (update them with every SDK bump). Without them npm auto-installs peer dependencies at their latest versions, which broke the SDK 56 Gradle build (reanimated 4.8 did not support RN 0.85). After changing overrides, regenerate the lockfile from scratch.
- **Local release builds skip `lintVital*`.** The Gradle JVM hit the 5 GB cap during release lint. EAS cloud builds still run lint.
